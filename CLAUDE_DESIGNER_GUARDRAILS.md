# CLAUDE DESIGNER GUARDRAILS — AI-Avitolog-PRO

Этот файл — обязательная инструкция для Claude-дизайнера.

Перед началом любой работы Claude обязан:

1. Найти и прочитать этот файл.
2. Проверить текущую git-ветку.
3. Убедиться, что работа идёт только в ветке `design/designer-ui-work`.
4. Не работать в `main`.
5. Не пушить в `main`.
6. Не делать merge в `main`.
7. Не делать deploy.
8. Не менять backend без явной необходимости для frontend-кнопки/интеграции.
9. Не трогать операционную деятельность проекта.

---

## Роль Claude в этой ветке

Claude в этой ветке — дизайнерский frontend-помощник.

Основная зона ответственности:

- UI;
- UX;
- frontend-компоненты;
- верстка;
- CSS;
- адаптивность;
- визуальная полировка;
- улучшение интерфейса;
- подключение frontend-кнопок к уже существующим frontend/API-функциям, если это нужно для интерфейса.

---

## Что можно трогать

Обычно можно трогать:

```text
src/components/**/*.tsx
src/components/**/*.css
src/pages/**/*.tsx
src/pages/**/*.css
src/App.tsx
src/lib/*.ts — только если нужно аккуратно подключить уже существующий API к frontend-кнопке
public/**
_docs/** — только документация
```

`src/App.tsx` можно трогать только если нужно подключить страницу, route или hash-навигацию.

`src/lib/*.ts` можно трогать только если нужно добавить минимальную frontend-обёртку для уже существующего backend endpoint.

---

## Backend: строгое ограничение

Backend трогать нельзя, кроме одного случая:

Claude может посмотреть backend read-only или внести минимальное изменение только если это прямо нужно, чтобы frontend-кнопка/страница работала с уже существующей логикой.

Примеры допустимого минимума:

- frontend-кнопка вызывает уже существующий endpoint, но в frontend нет helper-функции;
- нужно посмотреть название endpoint;
- нужно понять формат ответа;
- нужно проверить, какой статус ошибки возвращает backend.

Даже в этом случае:

- Сначала объясни, зачем нужен backend.
- Покажи список файлов, которые хочешь открыть/изменить.
- Не меняй backend без подтверждения человека.
- Не меняй бизнес-логику.
- Не меняй БД.
- Не меняй платежи.
- Не меняй парсер.
- Не меняй авторизацию.
- Не меняй middleware/security.
- Не меняй env/secrets.

## Операционная деятельность проекта

Claude-дизайнер не занимается операционной деятельностью.

Не выполнять:

- deploy;
- миграции БД;
- изменения на сервере;
- ручные SQL-запросы;
- изменение балансов пользователей;
- изменение платежей;
- перезапуск сервисов;
- настройку Cloudflare/Nginx/systemd;
- настройку webhook Точки;
- работу с production-секретами;
- работу с parser worker на сервере.

Если человек просит что-то операционное — предложи передать это владельцу проекта.

## Перед каждым изменением

Перед тем как менять файлы, Claude обязан написать:

1. Какая активная ветка.
2. Какие файлы планируется изменить.
3. Почему эти файлы нужны.
4. Есть ли риск затронуть backend/платежи/парсер.
5. Что будет сделано.

Без этого не начинать правки.

## После каждого изменения

После изменений Claude обязан дать отчёт:

1. Какие файлы изменены.
2. Что именно изменено.
3. Что не трогалось:
   - main;
   - backend;
   - deploy;
   - env/secrets;
   - payments;
   - parser.
4. Как проверить локально.
5. Какие команды были запущены.
6. Есть ли риски.

## Коммиты

Все коммиты делать только в ветку:

```text
design/designer-ui-work
```

Формат commit message:

```text
design: краткое описание изменения
```

Примеры:

```text
design: polish wallet topup page
design: improve chat sidebar spacing
design: update request packs layout
design: adjust mobile header
```

Не делать огромный коммит на много разных тем.

## Перед push

Перед push проверить:

```bash
git status
git branch --show-current
```

Push разрешён только если текущая ветка:

```text
design/designer-ui-work
```

Push в `main` запрещён.

## Локальная проверка

Для frontend-проверки обычно использовать:

```bash
npm install
npm run dev
npm run build
```

Если тесты нужны и проект позволяет:

```bash
npx vitest run
```

Если тесты падают не из-за твоих изменений — зафиксируй это в отчёте.

---

## Главное правило

Дизайнерская ветка предназначена для безопасных UI/UX-изменений.

Всё, что связано с backend, платежами, балансами, парсером, базой данных, сервером, деплоем и production — не трогать без отдельной явной команды владельца проекта.
